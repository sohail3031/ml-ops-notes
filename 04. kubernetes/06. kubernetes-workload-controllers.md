So far, we have been running individual Pods. However, Pods are **ephemeral**, meaning they can fail, terminate, or be evicted at any time.

To maintain application availability, Kubernetes uses **controllers** to continuously work toward a desired state. These controllers can create, replace, scale, and update Pods automatically.

In this topic, we will look at three important Kubernetes workload controllers:

- **ReplicaSets**    
- **DaemonSets**
- **Deployments**

These controllers help run highly available and scalable workloads in Kubernetes.

## ReplicaSets

A **ReplicaSet** is a Kubernetes object that ensures a specified number of identical Pod replicas are running at any given time.

Running multiple replicas of a Pod provides several benefits:

- **High availability:** If one Pod fails, other Pods can continue handling the workload.
- **Scalability:** More Pod replicas allow the application to process more requests.
- **Load distribution:** Traffic can be distributed across multiple Pods instead of overloading a single Pod.
- **Self-healing:** If a managed Pod fails, the ReplicaSet creates a replacement to maintain the desired number of replicas.

Without a ReplicaSet, you would need to:

- Create a separate Pod manifest for every replica.
- Manually monitor Pods.
- Manually recreate Pods when they fail.

A ReplicaSet automates this process by continuously maintaining the desired number of Pod replicas.

## ReplicaSet Configuration

A ReplicaSet belongs to the `apps` API group, so its `apiVersion` is:

```yaml
apiVersion: apps/v1
```

The resource type is:

```yaml
kind: ReplicaSet
```

A ReplicaSet manifest typically includes:

- `replicas` — The desired number of Pods.
- `selector` — Identifies the Pods managed by the ReplicaSet.
- `template` — Defines the Pod template used to create new Pods.

Example:

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: dev-rs

spec:
  replicas: 3

  selector:
    matchLabels:
      app: web-server

  template:
    metadata:
      labels:
        app: web-server

    spec:
      containers:
        - name: dev-nginx
          image: nginx:latest
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
              protocol: TCP

      restartPolicy: Always
      dnsPolicy: ClusterFirst
```

> [!note]  
> The `.spec.template` section is similar to a Pod manifest. However, it does not include the Pod's top-level `apiVersion`, `kind`, or `metadata.name` fields because the ReplicaSet generates and manages the Pods.

## ReplicaSet Selectors

A ReplicaSet uses a **label selector** to identify the Pods that it manages.

You can view Pod labels with:

```bash
kubectl get pods --show-labels -n hyper
```

Example output:

```text
NAME           READY   STATUS    RESTARTS   AGE   LABELS
dev-rs-c6gl5   1/1     Running   0          24s   app=web-server
dev-rs-f2hwj   1/1     Running   0          24s   app=web-server
dev-rs-wsqcr   1/1     Running   0          24s   app=web-server
```

You can filter Pods using a label selector:

```bash
kubectl get pods --selector app=web-server
```

This works similarly to how a ReplicaSet finds the Pods it manages.

### `matchLabels`

The `matchLabels` selector uses exact key-value matches:

```yaml
selector:
  matchLabels:
    app: web-server
```

### `matchExpressions`

You can also use `matchExpressions`, which provides a more flexible, operator-based syntax.

Example:

```yaml
selector:
  matchExpressions:
    - key: app
      operator: In
      values:
        - web-server
```

Common operators include:

- `In`
- `NotIn`
- `Exists`
- `DoesNotExist`

## Scaling a ReplicaSet

After deploying a ReplicaSet, you can check its status with:

```bash
kubectl get replicasets
```

Example output:

```text
NAME     DESIRED   CURRENT   READY   AGE
dev-rs   3         3         3       14s
```

You can scale a ReplicaSet declaratively by changing the `.spec.replicas` value in its manifest and applying the updated file.

You can also scale it imperatively:

```bash
kubectl scale rs dev-rs --replicas 7
```

After scaling:

```text
NAME     DESIRED   CURRENT   READY   AGE
dev-rs   7         7         7       114s
```

To delete a ReplicaSet, use:

```bash
kubectl delete -f <replicaset-manifest.yaml>
```

## DaemonSets

A ReplicaSet runs a specified number of Pod replicas, regardless of which nodes those Pods are scheduled on.

A **DaemonSet** is different. It ensures that a copy of a Pod runs on:

- Every eligible node in the cluster, or
- A specific subset of nodes.

DaemonSets are useful for workloads that need to run directly on cluster nodes, such as:

- Log collection agents
- Monitoring agents
- Network plugins
- Security agents

## DaemonSet Configuration

Like ReplicaSets, DaemonSets belong to the `apps/v1` API group.

A DaemonSet can use a configuration similar to the following:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter

spec:
  selector:
    matchLabels:
      app: node-exporter

  template:
    metadata:
      labels:
        app: node-exporter
        tier: monitoring

    spec:
      hostNetwork: true
      hostPID: true

      containers:
        - name: node-exporter
          image: prom/node-exporter:latest
          args:
            - --path.procfs=/host/proc
            - --path.sysfs=/host/sys
            - --path.rootfs=/host/root

          ports:
            - containerPort: 9100
              name: metrics

          volumeMounts:
            - name: proc
              mountPath: /host/proc
              readOnly: true

            - name: sys
              mountPath: /host/sys
              readOnly: true

            - name: root
              mountPath: /host/root
              readOnly: true

      volumes:
        - name: proc
          hostPath:
            path: /proc

        - name: sys
          hostPath:
            path: /sys

        - name: root
          hostPath:
            path: /
```

This configuration ensures that a copy of the Node Exporter agent runs on every eligible node.

You can verify the DaemonSet with:

```bash
kubectl get daemonsets
```

Example output:

```text
NAME            DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
node-exporter   3         3         3       3            3           <none>          102s
```

You can also view the Pods and the nodes on which they are running:

```bash
kubectl get pods -l app=node-exporter -o wide
```

Example output:

```text
NAME                  READY   STATUS    RESTARTS   AGE     IP             NODE
node-exporter-6tpzw   1/1     Running   0          7m36s   192.168.49.2   node-001
node-exporter-j6j6w   1/1     Running   0          7m36s   192.168.49.3   node-002
node-exporter-s6mc4   1/1     Running   0          7m36s   192.168.49.4   node-003
```

## Limiting a DaemonSet to Specific Nodes

Sometimes, you do not want a DaemonSet to run on every node.

You can restrict it to nodes with a specific label using a **node selector**.

First, add a label to the desired node:

```bash
kubectl label nodes <node-name> server=true
```

Example output:

```text
node/<node-name> labeled
```

Then, add a `nodeSelector` to the DaemonSet's Pod template:

```yaml
template:
  metadata:
    labels:
      name: fluentd

  spec:
    nodeSelector:
      server: "true"

    containers:
      - name: fluentd
        image: fluent/fluentd:latest
```

Now, only nodes with the label:

```text
server=true
```

will run a copy of the Pod.

Verify the Pods with:

```bash
kubectl get pods -l name=fluentd -o wide
```

Example output:

```text
NAME            READY   STATUS    RESTARTS   AGE   IP           NODE
fluentd-bhpvs   1/1     Running   0          62s   10.244.2.2   node-003
fluentd-v9sq7   1/1     Running   0          62s   10.244.1.2   node-002
```

To delete a DaemonSet, use:

```bash
kubectl delete -f <daemonset-manifest.yaml>
```

## Deployments

ReplicaSets and DaemonSets help ensure that the required Pods are running. However, Kubernetes also provides a higher-level controller for managing application updates.

A **Deployment** manages the lifecycle of an application in Kubernetes.

A Deployment can:

- Maintain the desired number of application replicas.
- Create and manage ReplicaSets.
- Perform controlled application updates.
- Roll out new versions gradually.
- Roll back to previous versions if necessary.
- Maintain application availability during updates.

The relationship between these resources is:

```text
Deployment
    │
    ▼
ReplicaSet
    │
    ▼
Pods
```

> [!important]  
> A Deployment manages ReplicaSets, and ReplicaSets manage Pods. In most application workloads, you should manage replicas through the Deployment rather than directly modifying the ReplicaSet created by the Deployment.

## Deployment Configuration

A Deployment looks similar to a ReplicaSet, but its resource type is `Deployment`.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hyperskill-clone
  namespace: hyper
  labels:
    app: hyper-app

  annotations:
    environment: "Production"

spec:
  replicas: 3

  selector:
    matchLabels:
      app: hyper-app

  template:
    metadata:
      labels:
        app: hyper-app

    spec:
      initContainers:
        - name: busybox
          image: busybox:latest
          imagePullPolicy: Always
          command: ["sh", "-c", "echo Initializing... && sleep 5"]

      containers:
        - name: frontend
          image: nginx:latest
          imagePullPolicy: Always

          ports:
            - containerPort: 80
              name: http
              protocol: TCP

          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
              ephemeral-storage: "1Gi"

        - name: hyperskill-backend
          image: initram/hyperskill-clone:latest
          imagePullPolicy: IfNotPresent

          ports:
            - containerPort: 8000
              protocol: TCP
              name: hyperskill

          env:
            - name: log-level
              value: "info"

          readinessProbe:
            httpGet:
              port: 8000
              path: /ready
            initialDelaySeconds: 5
            timeoutSeconds: 3
            failureThreshold: 2

          livenessProbe:
            httpGet:
              port: 8000
              path: /health
            failureThreshold: 3
            timeoutSeconds: 5
            periodSeconds: 10

          volumeMounts:
            - mountPath: /tmp/shared
              name: cache

          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"

      volumes:
        - name: cache
          emptyDir: {}
```

> [!note]  
> The Deployment example above contains an init container, two application containers, health probes, resource requests, and a shared `emptyDir` volume.

## Checking Deployment Ownership

After deploying the Deployment, you can check its status:

```bash
kubectl get deployments --show-labels
```

Example output:

```text

hyperskill-clone   3/3     3            3           2m57s   app=hyper-app
```

Check the ReplicaSets:

```bash

```

Example output:

```text

```

## Scaling a Deployment

When a ReplicaSet is managed by a Deployment, scale the **Deployment**, not the ReplicaSet.

For example:

```bash
kubectl scale deployment hyperskill-clone --replicas 4
```

The Deployment updates its desired state and manages the underlying ReplicaSet accordingly.

> [!warning]  
> If you manually scale a ReplicaSet managed by a Deployment, the Deployment controller may reconcile the state and override your manual changes.

# Update Strategies

Deployments and DaemonSets support different strategies for updating workloads.

## Deployment Strategies

A Deployment supports:

- `Recreate`
- `RollingUpdate`

### `Recreate`

The `Recreate` strategy terminates all existing Pods before creating Pods from the new version.

```yaml
spec:
  strategy:
    type: Recreate
```

This can cause a period of downtime because the old Pods are removed before the new Pods become available.

Use this strategy only when downtime is acceptable or when the application requires the old and new versions not to run simultaneously.

### `RollingUpdate`

`RollingUpdate` gradually replaces old Pods with new Pods.

A subset of Pods is updated at a time until all Pods run the new version.

Example:

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
```

The two important fields are:

- `maxSurge` — The maximum number of additional Pods that can be created above the desired number of replicas.
- `maxUnavailable` — The maximum number of Pods that can be unavailable during the update.

These values can be specified as:

- Integers
- Percentages

For example, if:

```text
replicas = 5
```

and:

```text
maxSurge = 25%
maxUnavailable = 25%
```

the effective values are calculated according to Kubernetes rounding rules, allowing only a limited number of additional or unavailable Pods during the rollout.

> [!note]  
> The exact number of Pods created or allowed to be unavailable can depend on how Kubernetes rounds percentage values.

## DaemonSet Update Strategies

A DaemonSet supports:

- `OnDelete`
- `RollingUpdate`

### `OnDelete`

With the `OnDelete` strategy, changing the DaemonSet template does not automatically update existing Pods.

New Pods are created with the updated configuration only after old Pods are manually deleted.

```yaml
spec:
  updateStrategy:
    type: OnDelete
```

### `RollingUpdate`

A DaemonSet can also update Pods gradually:

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
```

`maxUnavailable` specifies the maximum number of DaemonSet Pods that can be unavailable during the update.

# Triggering a Rollout

A new rollout is triggered when the Pod template changes.

The Pod template is located at:

```text
.spec.template
```

Examples of changes that trigger a rollout include:

- Changing a container image.
- Changing container configuration.
- Changing Pod labels or annotations in the template.
- Modifying other fields within the Pod template.

For example, you can update a container image imperatively:

```bash
kubectl set image deployment/hyperskill-clone \
  hyperskill-backend=initram/hyperskill-clone:v1
```

You can also modify the Deployment manifest and apply the changes.

## Checking Rollout Status

After triggering an update, check its status with:

```bash
kubectl rollout status deployment/hyperskill-clone
```

Example output:

```text
deployment "hyperskill-clone" successfully rolled out
```

## Viewing Rollout History

View the rollout history with:

```bash
kubectl rollout history deployment/hyperskill-clone
```

Example output:

```text
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
```

To view details about a specific revision:

```bash
kubectl rollout history deployment/hyperskill-clone --revision=2
```

## Rolling Back a Deployment

If a new version causes problems, you can undo the most recent rollout:

```bash
kubectl rollout undo deployment/hyperskill-clone
```

Example output:

```text
deployment.apps/hyperskill-clone rolled back
```

You can also roll back to a specific revision:

```bash
kubectl rollout undo deployment/hyperskill-clone --to-revision=2
```

> [!note]  
> Kubernetes tracks ReplicaSet revisions associated with Deployment rollouts. When you roll back, Kubernetes reuses a previous Pod template by creating or scaling the appropriate ReplicaSet and updates the rollout history accordingly.

## ReplicaSet vs DaemonSet vs Deployment

| Controller     | Main Purpose                                 | Pod Placement                         | Scaling                 | Updates                        |
| -------------- | -------------------------------------------- | ------------------------------------- | ----------------------- | ------------------------------ |
| **ReplicaSet** | Maintains a specified number of Pod replicas | Any eligible node                     | Change `replicas`       | No advanced rollout management |
| **DaemonSet**  | Runs one Pod on every eligible node          | Every eligible node or selected nodes | Based on eligible nodes | `OnDelete` or `RollingUpdate`  |
| **Deployment** | Manages application replicas and updates     | Any eligible node                     | Change `replicas`       | `Recreate` or `RollingUpdate`  |

## Conclusion

Kubernetes provides several controllers for running reliable and replicated workloads.

- **ReplicaSets** maintain a specified number of Pod replicas, providing self-healing, scalability, and improved availability.
- **DaemonSets** ensure that a Pod runs on every eligible node or on a selected subset of nodes.
- **Deployments** manage ReplicaSets and provide controlled, declarative application updates and rollbacks.

Deployments support the `Recreate` and `RollingUpdate` strategies:

- `Recreate` removes existing Pods before creating new ones and may cause downtime.
- `RollingUpdate` gradually replaces Pods to maintain availability during an update.

DaemonSets support the `OnDelete` and `RollingUpdate` strategies:

- `OnDelete` updates Pods only after existing Pods are manually deleted.
- `RollingUpdate` gradually updates Pods across eligible nodes.

These controllers are fundamental to running highly available, scalable, and maintainable workloads in Kubernetes.
