# Introduction

Previously, we discussed how to expose applications running in Kubernetes to the outside world using Services of type `NodePort` and `LoadBalancer`.

However, what happens when you have multiple applications running in your cluster, each with its own exposed Service?

- With `NodePort` Services, each exposed Service requires a unique port.    
- With `LoadBalancer` Services, each exposed Service requires its own load balancer, which can become expensive and inefficient.

The **Ingress** resource solves this problem by allowing multiple HTTP and HTTPS Services to be exposed through a single external entry point.

---

## Introduction to Ingress

A Kubernetes **Service** primarily operates at **Layer 4 (Transport Layer)** of the OSI model.

This means it forwards TCP and UDP traffic based on:

- IP address    
- Port number

It does not inspect the contents of an HTTP request.

Because of this, exposing multiple HTTP applications using only Services can require multiple external entry points.

**Ingress** is a Kubernetes API object that provides HTTP and HTTPS routing to Kubernetes Services.

Ingress operates at the **application layer (Layer 7)**, allowing it to inspect HTTP traffic and route requests based on rules such as:

- Hostnames
- URL paths

Ingress provides a mechanism for exposing multiple Services to the outside world through a **single IP address**.

It can also support:

- TLS termination
- HTTPS traffic
- Automated SSL/TLS certificate management using tools such as `cert-manager`

> [!note]  
> TLS and automated certificate management are not covered in this topic.

You can think of an **Ingress** as a **Layer 7 load balancer for Kubernetes Services**.

## Without and With Ingress

Without Ingress, multiple applications may require multiple external Services and load balancers.

With Ingress:

```text
                    Internet
                       |
                       v
              +----------------+
              | Load Balancer  |
              |   / Ingress    |
              +----------------+
                       |
          +------------+------------+
          |                         |
          v                         v
    +-----------+             +-----------+
    | app-home  |             |  app-api  |
    |  Service  |             |  Service  |
    +-----------+             +-----------+
```

With this approach, only a single external load balancer is required. Ingress rules determine how incoming requests are routed to different Services.

---

# Preparing for Ingress

Unlike most Kubernetes objects, Ingress consists of two separate components:

1. **Ingress Resource**    
2. **Ingress Controller**

## Ingress Resource

The Ingress resource defines the routing rules.

For example:

- Requests for a particular hostname can be routed to one Service.
- Requests for a specific URL path can be routed to another Service.

## Ingress Controller

An **Ingress Controller** is responsible for implementing and enforcing the rules defined in the Ingress resource.

Kubernetes does not include an Ingress Controller by default.

However, managed Kubernetes services such as:

- GKE
- AKS
- EKS

may provide or simplify the installation of an Ingress Controller.

For self-managed or local Kubernetes clusters, you need to install an Ingress Controller manually.

Popular Ingress Controllers include:

- HAProxy
- Contour
- Cilium
- NGINX-based controllers
- Other third-party Ingress Controllers

> [!important]  
> Your cluster must support creating Services of type `LoadBalancer` and provide an external IP, or otherwise provide an equivalent mechanism for exposing the Ingress Controller.

---

## Enabling Ingress in Minikube

Minikube provides an Ingress Controller as an addon.

Enable it with:

```shell
minikube addons enable ingress
```

---

## Installing Contour on Kind

For a Kind cluster, you can use **Contour** as the Ingress Controller.

Install it with:

```shell
kubectl apply -f https://projectcontour.io/quickstart/contour.yaml
```

Verify that the Contour pods are running:

```shell
kubectl get pods -n projectcontour -o wide
```

You can also verify the `LoadBalancer` Service created for Envoy:

```shell
kubectl get -n projectcontour svc envoy -o wide
```

Example output:

```text
NAME    TYPE           CLUSTER-IP       EXTERNAL-IP    PORT(S)                      AGE     SELECTOR
envoy   LoadBalancer   34.118.231.186   34.163.12.68   80:30624/TCP,443:32665/TCP   2m48s   app=envoy
```

The Envoy Service acts as the external entry point for traffic entering the cluster.

# Creating Applications for Ingress

Before creating an Ingress resource, we need to create some Deployments and Services.

We will create two applications:

- `app-home`    
- `app-api`

---

## app-home Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-home
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-home
  template:
    metadata:
      labels:
        app: app-home
    spec:
      containers:
        - image: hashicorp/http-echo:latest
          name: http-echo
          ports:
            - containerPort: 5678
          args:
            - "-text=Hello from Home service."
```

This Deployment creates two replicas of the `app-home` application.

---

## app-api Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-api
  template:
    metadata:
      labels:
        app: app-api
    spec:
      containers:
        - image: hashicorp/http-echo:latest
          name: http-echo
          ports:
            - containerPort: 5678
          args:
            - "-text=Hello from API service."
```

This Deployment creates two replicas of the `app-api` application.

---

# Exposing the Deployments

Expose the `app-home` Deployment:

```shell
kubectl expose deploy app-home --port 80 --target-port 5678
```

For local testing, you can access the Service using port forwarding:

```shell
kubectl port-forward svc/app-home 80
```

The same approach can be used to expose the `app-api` Deployment.

These commands create `ClusterIP` Services, which are accessible only from within the Kubernetes cluster.

Next, we can create Ingress rules to route external traffic to these Services.

There are two common types of routing:

1. **Host-based routing**    
2. **Path-based routing**

---

# Host-Based Routing

Host-based routing directs traffic based on the `Host` header in an incoming HTTP request.

The `Host` header contains the domain name requested by the client.

For example:

```text
app-home.local
```

or:

```text
app-api.local
```

The following Ingress configuration routes traffic based on the hostname.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: host-ingress
spec:
  rules:
    - host: app-home.local
      http:
        paths:
          - pathType: Prefix
            path: /
            backend:
              service:
                name: app-home
                port:
                  number: 80

    - host: app-api.local
      http:
        paths:
          - pathType: Prefix
            path: /
            backend:
              service:
                name: app-api
                port:
                  number: 80
```

With these rules:

```text
app-home.local
        |
        v
    app-home
    Service
```

```text
app-api.local
        |
        v
     app-api
     Service
```

---

## Configuring the Hosts File

To resolve `app-home.local` and `app-api.local`, you need to map these hostnames to the external IP address of the Ingress Controller's load balancer.

For Minikube, you can use the output of:

```shell
minikube ip
```

The location of the `hosts` file depends on your operating system.

### Linux and macOS

```text
/etc/hosts
```

### Windows

```text
C:\Windows\System32\drivers\etc\hosts
```

Administrator or root privileges are required to modify this file.

Add the following entry:

```text
<ip-address> app-home.local app-api.local
```

Replace `<ip-address>` with the external IP address of your Ingress Controller or load balancer.

> [!warning]  
> Remember to remove these entries from your `hosts` file when you no longer need them.

On macOS, you may also need to flush the DNS cache after modifying the `hosts` file:

```shell
sudo killall -HUP mDNSResponder
```

After configuring the hostnames, you can access:

```text
http://app-home.local/
```

and:

```text
http://app-api.local/
```

Both applications use the same external IP address, but the Ingress Controller routes the requests to different Services based on the hostname.

# Path-Based Routing

Path-based routing directs traffic based on the URL path of an incoming HTTP request.

For example:

```text
/dashboard
```

or:

```text
/api
```

The following Ingress configuration routes requests based on the URL path:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: path-ingress
spec:
  rules:
    - http:
        paths:
          - path: /dashboard
            pathType: Exact
            backend:
              service:
                name: app-home
                port:
                  number: 80

          - path: /api
            pathType: Exact
            backend:
              service:
                name: app-api
                port:
                  number: 80
```

With this configuration:

```text
/dashboard
     |
     v
app-home Service
```

```text
/api
  |
  v
app-api Service
```

For example:

```text
http://example.com/dashboard
```

is routed to:

```text
app-home Service
```

While:

```text
http://example.com/api
```

is routed to:

```text
app-api Service
```

---

# Understanding `pathType`

The `pathType` field determines how a URL path is matched.

It has three possible values:

- `Prefix`    
- `Exact`
- `ImplementationSpecific`

## `Prefix`

With:

```yaml
pathType: Prefix
```

The rule matches requests whose path begins with the specified path, based on URL path segments separated by `/`.

For example:

```yaml
path: /api
pathType: Prefix
```

can match paths such as:

```text
/api
/api/users
/api/products
```

---

## `Exact`

With:

```yaml
pathType: Exact
```

The request path must match the specified path exactly.

For example:

```yaml
path: /api
pathType: Exact
```

matches:

```text
/api
```

but does not match:

```text
/api/users
```

---

## `ImplementationSpecific`

With:

```yaml
pathType: ImplementationSpecific
```

the Ingress Controller or `IngressClass` determines how the path should be interpreted.

This allows different controllers to provide custom routing behavior.

For example, some controllers may support additional matching mechanisms such as:

- Regular expressions    
- Controller-specific routing rules

> [!note]  
> The exact behavior of `ImplementationSpecific` depends on the Ingress Controller being used.

---

# Advanced Routing

More advanced routing features are not part of the core Kubernetes Ingress API.

Examples include:

- Header-based routing    
- HTTP method-based routing
- Weighted traffic splitting
- Advanced traffic management

Ingress Controllers may provide these capabilities through:

- Controller-specific annotations
- Custom configuration
- Additional APIs

For more advanced traffic routing, the **Kubernetes Gateway API** provides a more flexible and extensible approach.

---

# Ingress Workflow

The overall request flow can be summarized as follows:

```text
Client
   |
   v
External IP
   |
   v
Load Balancer
   |
   v
Ingress Controller
   |
   |--- Host/Path Rules ---|
   |                       |
   v                       v
app-home Service      app-api Service
   |                       |
   v                       v
app-home Pods         app-api Pods
```

# Key Takeaways

- Kubernetes Services primarily operate at **Layer 4** and route traffic based on IP addresses and ports.    
- Ingress operates at **Layer 7** and can route HTTP and HTTPS traffic based on hostnames and URL paths.
- An Ingress resource allows multiple Services to be exposed through a single external IP address.
- An **Ingress Controller** is required to implement the rules defined in an Ingress resource.
- Kubernetes does not include an Ingress Controller by default.
- Common Ingress Controllers include Contour, HAProxy, Cilium, and other third-party implementations.
- `ClusterIP` Services can be used as backend Services for an Ingress.
- **Host-based routing** directs traffic based on the requested hostname.
- **Path-based routing** directs traffic based on the URL path.
- `pathType` can be:
    - `Prefix`
    - `Exact`
    - `ImplementationSpecific`
- Ingress can support features such as TLS termination.
- A single Ingress Controller can serve as the external entry point for multiple HTTP and HTTPS applications.
- Advanced traffic routing requirements may be better handled using controller-specific features or the Kubernetes Gateway API.

---

# Conclusion

Kubernetes Ingress provides a flexible and cost-effective way to expose multiple HTTP and HTTPS applications to the outside world.

Instead of creating multiple `NodePort` Services with different ports or multiple `LoadBalancer` Services with separate load balancers, Ingress allows multiple backend Services to share a single external entry point.

The Ingress architecture consists of two main components:

1. The **Ingress resource**, which defines the desired routing rules.
2. The **Ingress Controller**, which implements those rules.

Using host-based and path-based routing, an Ingress Controller can route incoming traffic to the appropriate Kubernetes Services. Combined with features such as TLS termination, Ingress provides a centralized entry point for HTTP and HTTPS traffic into a Kubernetes cluster.
