# Running Stateful Applications in Kubernetes

The workloads we have worked with so far have been disposable and replaceable. This design principle allows Kubernetes to scale, heal, and reschedule workloads seamlessly across the cluster.

However, some workloads depend on persistent data, such as databases, message queues, and file storage. Running these workloads reliably requires a way to attach durable storage and preserve workload identity across restarts.

In this topic, we examine how to run **stateful applications** on Kubernetes.

---

## PersistentVolumes

Kubernetes provides a layered set of storage primitives that decouple storage from the lifecycle of a Pod and from the underlying infrastructure.

It supports many volume types, ranging from local storage to network and cloud storage. Previously, we saw how `emptyDir` can be used as temporary storage. An `emptyDir` volume is created when a Pod starts, but its data is lost when the Pod is deleted.

This is where **PersistentVolumes (PVs)** come in.

A **PersistentVolume (PV)** is a piece of storage in the cluster that has been provisioned manually by an administrator or dynamically using a storage provisioner.

A PV has a lifecycle independent of the Pods that use it. It is a cluster-level resource, similar to a Node, but used for storage.

A PV represents an actual piece of storage, such as:

- An NFS share
- An AWS EBS volume
- A Google Persistent Disk
- Local storage

### PersistentVolume Example

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-database
spec:
  capacity:
    storage: 5Gi

  accessModes:
    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  storageClassName: local-storage

  local:
    path: /mnt/data

  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - node-1
                - node-2
```

### PersistentVolume Capacity

The `capacity` field defines the amount of storage available.

```yaml
capacity:
  storage: 5Gi
```

### PersistentVolume Access Modes

The `accessModes` field specifies how the volume can be mounted.

- `ReadWriteOnce` (`RWO`) — The volume can be mounted as read-write by a single node.
- `ReadOnlyMany` (`ROX`) — The volume can be mounted as read-only by multiple nodes.
- `ReadWriteMany` (`RWX`) — The volume can be mounted as read-write by multiple nodes.
- `ReadWriteOncePod` (`RWOP`) — The volume can be mounted as read-write by a single Pod.

### PersistentVolume Reclaim Policy

The `persistentVolumeReclaimPolicy` defines what happens to a PV when its claim is released.

- `Retain` — Keeps the underlying storage and data.
- `Delete` — Deletes the underlying storage and data.

Each PV may have additional requirements depending on its storage type.

For example, when using `local-storage`, Kubernetes needs node constraints because local storage physically exists on a specific node.

Usually, cluster administrators provision PersistentVolumes. As a developer, you typically request storage using a **PersistentVolumeClaim (PVC)**.

You can view available PersistentVolumes using:

```bash
kubectl get persistentvolumes
```

## PersistentVolumeClaims

Once a PersistentVolume is available, an application can request storage with specific properties using a **PersistentVolumeClaim (PVC)**.

A useful comparison is:

- A Pod consumes compute resources such as CPU and memory.
- A PVC consumes storage resources provided by a PV.

PVCs allow you to specify storage requirements without worrying about the underlying storage implementation.

### PersistentVolumeClaim Example

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-003
spec:
  accessModes:
    - ReadWriteOnce

  storageClassName: local-storage

  resources:
    requests:
      storage: 2Gi
```

When a PVC is created, Kubernetes searches for a PV that satisfies the requested requirements and binds them together.

A matching PV must satisfy requirements such as:

- Storage capacity
- Access mode
- Storage class

Once bound, the PVC can be referenced from a Pod like any other volume.

> [!NOTE]  
> A PVC is a namespaced resource. A Pod can only reference a PVC within the same namespace.

The `storageClassName` must also match between the PV and PVC, or the appropriate default/no-class behavior must be used.

# Dynamic Storage Provisioning

Manually creating PersistentVolumes for every storage request is tedious and does not scale well.

**StorageClasses** solve this problem by enabling **dynamic storage provisioning**.

With dynamic provisioning:

1. A PVC requests storage.
2. Kubernetes identifies the appropriate `StorageClass`.
3. The storage provisioner creates the underlying storage.
4. Kubernetes creates a matching PV.
5. The PV is bound to the PVC.

A `StorageClass` describes a type of storage offered by the cluster.

It specifies:

- The provisioner responsible for creating the storage.
- Parameters required by the provisioner.
- A reclaim policy.
- A volume binding mode.

## StorageClass Example

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nfs-provisioner

provisioner: nfs.csi.k8s.io

parameters:
  server: <server_ip> # Replace with the actual value.
  share: /mnt/<share_name> # Replace with the actual value.

reclaimPolicy: Delete

volumeBindingMode: WaitForFirstConsumer
```

In this example, Kubernetes uses an NFS CSI provisioner to provide NFS storage.

You can view available StorageClasses using:

```bash
kubectl get storageclasses
```

Example output:

```text
NAME              PROVISIONER      RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
nfs-provisioner   nfs.csi.k8s.io   Delete          WaitForFirstConsumer   false                  14m
```

To use a StorageClass, a PVC references it by name in the `storageClassName` field.

For example:

```yaml
storageClassName: nfs-provisioner
```

When a PVC requests storage matching the StorageClass, Kubernetes automatically provisions a PV without requiring manual intervention.

### Volume Binding Modes

#### `WaitForFirstConsumer`

Storage is provisioned only when a Pod that uses the PVC is scheduled.

This is particularly useful when storage placement depends on where the Pod is scheduled.

#### `Immediate`

Storage is provisioned immediately when the PVC is created.

You can view PersistentVolumes created through dynamic provisioning using:

```bash
kubectl get pv
```

Example output:

```text
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM       STORAGECLASS      AGE
pvc-2e1a784d-7d4f-4c78-89ea-cdfaeb1fa011   1Gi        RWO            Delete          Bound    nfs-claim   nfs-provisioner   10h
```

For the NFS setup to work, a valid NFS server must be available and accessible to the Kubernetes cluster.

# StatefulSets

Persistent storage solves only half of the stateful workload problem.

The other half is **identity**.

Consider a database cluster with three replicas. Each replica may require:

- A specific identity.
- A dedicated data volume.
- A stable network name.
- A predictable startup and shutdown order.

A Deployment treats Pods as interchangeable, making it unsuitable for workloads that require stable identities.

This is where **StatefulSets** are used.

A StatefulSet provides:

## Stable and Unique Network Identifiers

Pods are named predictably using the following format:

```text
<statefulset-name>-<ordinal>
```

For example:

```text
mysql-0
mysql-1
mysql-2
```

Each Pod receives a stable identity and network hostname.

## Stable and Persistent Storage

Each Pod receives its own PersistentVolumeClaim created from a `volumeClaimTemplates` section.

If a Pod is deleted or rescheduled, the replacement Pod can reattach to the same PVC.

## Ordered Deployment and Scaling

Pods are created and terminated in a predictable order.

For example:

```text
Creation:
mysql-0 → mysql-1 → mysql-2

Termination:
mysql-2 → mysql-1 → mysql-0
```

---

## StatefulSet Example

The following example creates a StatefulSet for a MySQL database.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql

spec:
  serviceName: mysql-headless
  replicas: 3

  selector:
    matchLabels:
      app: mysql

  template:
    metadata:
      labels:
        app: mysql

    spec:
      containers:
        - name: mysql
          image: mysql:9.7.0-oracle

          ports:
            - containerPort: 3306

          env:
            - name: MYSQL_ROOT_PASSWORD
              value: "hyper2026"

          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql

  volumeClaimTemplates:
    - metadata:
        name: data

      spec:
        accessModes:
          - ReadWriteOnce

        storageClassName: dev-sc

        resources:
          requests:
            storage: 1Gi
```

The `serviceName` field references a **headless Service**.

A headless Service uses:

```yaml
clusterIP: None
```

This allows each StatefulSet Pod to have a stable DNS record.

For example:

```text
mysql-0.mysql-headless.default.svc.cluster.local
```

---

## `volumeClaimTemplates`

The `volumeClaimTemplates` section does not create a single PVC.

Instead, it acts as a template that Kubernetes uses to create one PVC for each StatefulSet Pod.

For the MySQL StatefulSet:

```text
Pod          PVC
───────      ─────────────
mysql-0  →   data-mysql-0
mysql-1  →   data-mysql-1
mysql-2  →   data-mysql-2
```

Each PVC is backed by its own PersistentVolume.

If `mysql-1` is deleted:

1. The StatefulSet creates a replacement Pod named `mysql-1`.
2. The Pod retains the same stable identity.
3. The Pod reattaches to the existing `data-mysql-1` PVC.

This ensures that the Pod can continue using its original persistent data.

> [!IMPORTANT]  
> Deleting a StatefulSet does not delete its PVCs by default, helping preserve application data.

# Summary

Kubernetes provides several building blocks for running stateful workloads.

## PersistentVolumes

**PersistentVolumes (PVs)** provide storage that is independent of the lifecycle of individual Pods.

## PersistentVolumeClaims

**PersistentVolumeClaims (PVCs)** allow applications to request storage based on requirements such as capacity and access mode.

## StorageClasses

**StorageClasses** enable dynamic storage provisioning, eliminating the need to manually create a PersistentVolume for every storage request.

## StatefulSets

**StatefulSets** are designed for workloads that require:

- Stable identities.
- Stable network names.
- Persistent storage.
- One dedicated volume per replica.
- Ordered deployment and scaling.

Together, **PersistentVolumes, PersistentVolumeClaims, StorageClasses, and StatefulSets** allow Kubernetes to run stateful workloads while maintaining persistent storage and stable application identities.
