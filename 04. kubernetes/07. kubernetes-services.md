Kubernetes is a highly dynamic system where Pods can be created, terminated, rescheduled, or replaced at any time. Because Pods are ephemeral, connecting directly to a Pod using its IP address is unreliable.

For example, you may connect to a Pod using a particular IP address, but that Pod may later be deleted or rescheduled and receive a different IP address. Kubernetes **Services** solve this problem by providing a stable networking endpoint for applications.

## Services

An application in Kubernetes may run as a Deployment with multiple Pod replicas. Each Pod has its own IP address, but these IP addresses can change when Pods are:

- Deleted    
- Recreated
- Rescheduled
- Scaled up or down

This makes it difficult for other applications to know which Pod IP address they should connect to.

A **Service** provides a stable way to access a group of Pods through a single endpoint.

```text
Client
   │
   ▼
Service
   │
   ├── Pod 1
   ├── Pod 2
   └── Pod 3
```

A Service defines a set of **endpoints**, which are often Pods but can also represent other destinations.

When a client sends a request to a Service, Kubernetes forwards the request to one of the available backend endpoints.

An additional benefit is that applications inside the Kubernetes cluster do not usually need to use the Service's IP address directly. They can use the **Service name**, which Kubernetes DNS resolves to the Service's IP address.

> [!important]  
> A Service provides a stable endpoint, while the Pods behind the Service can be dynamically created, removed, or replaced.

Services identify the Pods they should target by using **label selectors**, similar to how ReplicaSets identify the Pods they manage.

## Kubernetes Service Types

Kubernetes provides several Service types:

- `ClusterIP`
- `NodePort`
- `LoadBalancer`
- `ExternalName`

Each Service type is designed for a different networking use case.

Before exploring each type, let's look at a basic Service manifest.

# The Service Manifest

A Service is a Kubernetes object that can be created and managed using YAML manifests or the `kubectl` command-line tool.

Example Service manifest:

```yaml
apiVersion: v1
kind: Service

metadata:
  name: myapp-service

spec:
  # Sends traffic to Pods with the label: app=web-server
  selector:
    app: web-server

  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080

  type: ClusterIP
```

The important fields are:

- `type` — Specifies the type of Service.
- `selector` — Identifies the Pods that should receive traffic.
- `port` — The port exposed by the Service.
- `targetPort` — The port on which the application inside the target Pod listens.

In this example, the Service forwards traffic only to Pods with the following label:

```yaml
app: web-server
```

Apply the Service manifest using:

```bash
kubectl apply -f svc.yaml
```

## Creating a Service Imperatively

You can also create a Service by exposing an existing Deployment:

```bash
kubectl expose deployment <deployment-name> \
  --type=ClusterIP \
  --name=<service-name> \
  --target-port=8080 \
  --port=80
```

If you do not specify the `--type` option, Kubernetes creates a `ClusterIP` Service by default.

You can verify that the Service was created successfully with:

```bash
kubectl get svc <service-name>
```

Example:

```bash
kubectl get svc web-server
```

Example output:

```text
NAME         TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE   SELECTOR
web-server   ClusterIP   34.118.226.21   <none>        80/TCP    55s   app=web-server
```

The `CLUSTER-IP` is automatically assigned by Kubernetes and provides a stable internal address for the Service.

# Understanding `port` and `targetPort`

The `ports` section of a Service manifest commonly includes `port` and `targetPort`.

```yaml
ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
```

## `port`

The `port` field represents the port exposed by the Service.

Other Pods inside the cluster can communicate with the application using:

```text
<Service-IP>:<port>
```

For example:

```text
34.118.226.21:80
```

## `targetPort`

The `targetPort` field represents the port on which the application inside the target Pod is listening.

For example:

```text
8080
```

The traffic flow is:

```text
Client Pod
    │
    ▼
Service IP:port
    │
    ▼
Pod IP:targetPort
```

For example:

```text
Service: 34.118.226.21:80
              │
              ▼
Pod: 10.177.129.9:8080
```

# ClusterIP

`ClusterIP` is the default Kubernetes Service type.

A ClusterIP Service allows applications and other Services to communicate **inside the Kubernetes cluster**.

```text
Pod A
  │
  │ Request
  ▼
Service
ClusterIP:port
  │
  ├── Pod 1: targetPort
  ├── Pod 2: targetPort
  └── Pod 3: targetPort
```

ClusterIP Services are ideal for:

- Communication between microservices.
- Communication between backend applications.
- Internal APIs.
- Internal databases.
- Other services that should not be directly exposed outside the cluster.

## Viewing Service Endpoints

You can view the endpoints associated with a Service using:

```bash
kubectl get endpointslices
```

Example output:

```text
NAME               ADDRESSTYPE   PORTS   ENDPOINTS                                   AGE
web-server-l759w   IPv4          8080    10.177.129.9,10.177.128.30,10.177.128.203   15m
```

In this example, the Service targets three Pods:

```text
10.177.129.9
10.177.128.30
10.177.128.203
```

As the Deployment scales, Kubernetes automatically updates the Service's available endpoints.

```text
Deployment scales
       │
       ▼
Pods are added or removed
       │
       ▼
EndpointSlices are updated
       │
       ▼
Service routes traffic to the current Pods
```

> [!note]  
> Applications should generally communicate through the Service rather than directly using individual Pod IP addresses.

# NodePort

A **NodePort** Service makes an application accessible externally through a specific port on the Kubernetes nodes.

The traffic flow is generally:

```text
External Client
       │
       ▼
Node IP:nodePort
       │
       ▼
Service
       │
       ▼
ClusterIP:port
       │
       ▼
Pod IP:targetPort
```

If an external client can reach a Kubernetes node, it can access the Service using:

```text
<Node-IP>:<nodePort>
```

The Service then forwards the traffic to one of the backend Pods.

## NodePort Configuration

A NodePort Service builds on top of the `ClusterIP` Service type.

When you create a NodePort Service, Kubernetes also provides internal Service networking so that traffic can eventually reach the target Pods.

You can specify a `nodePort` in the Service manifest:

```yaml
apiVersion: v1
kind: Service

metadata:
  name: myapp-service

spec:
  type: NodePort

  selector:
    app: web-server

  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
      nodePort: 30080
```

You can also create a NodePort Service imperatively.

The default NodePort range is:

```text
30000-32767
```

If you do not specify a particular `nodePort`, Kubernetes automatically assigns one from the configured NodePort range.

> [!tip]  
> NodePort is commonly useful for development, testing, debugging, and environments where a cloud load balancer is unavailable.

# LoadBalancer

A **LoadBalancer** Service exposes an application externally and integrates with a load-balancing implementation.

It is commonly used to make applications reachable from outside the Kubernetes cluster.

```text
External Client
       │
       ▼
External Load Balancer
       │
       ▼
NodePort
       │
       ▼
ClusterIP Service
       │
       ▼
Pods
```

Kubernetes itself does not provide a universal external load balancer implementation. A load balancer must be provided by the environment or infrastructure.

## Managed Kubernetes

On managed Kubernetes platforms, a cloud provider can automatically provision a load balancer when you create a Service of type `LoadBalancer`.

Examples include:

- [Google Kubernetes Engine (GKE)](https://cloud.google.com/kubernetes-engine?utm_source=chatgpt.com)    
- [Amazon Elastic Kubernetes Service (EKS)](https://aws.amazon.com/eks/?utm_source=chatgpt.com)

Example events:

```bash
kubectl get events \
  -o custom-columns='TYPE:.type,OBJECT:.involvedObject.name,SOURCE:.source.component,MESSAGE:.message'
```

Example output:

```text
TYPE     OBJECT   SOURCE               MESSAGE
Normal   mysvc    clouddns-controller  DNS records updated
Normal   mysvc    service-controller   Ensuring load balancer
Normal   mysvc    service-controller   Ensured load balancer
```

## LoadBalancer on Local Clusters

For local Kubernetes environments, additional tools or configuration may be required.

### Minikube

For Minikube, you can use:

```bash
minikube tunnel
```

This command allows `LoadBalancer` Services to receive externally accessible addresses in a local Minikube environment.

### Kind

For Kind clusters, you may need an additional load-balancer implementation, such as Cloud Provider KIND.

> [!note]  
> Local Kubernetes clusters do not automatically have access to the same cloud load-balancing infrastructure available in managed Kubernetes services.

## Viewing a LoadBalancer Service

Example:

```bash
kubectl get svc
```

Example output:

```text
NAME       TYPE           CLUSTER-IP       EXTERNAL-IP    PORT(S)        AGE
my-svc     LoadBalancer   34.118.237.158   34.155.81.80   80:32623/TCP   25h
```

The `EXTERNAL-IP` can be used by external clients to access the application.

> [!important]  
> Deleting a `LoadBalancer` Service may also trigger the removal of the externally provisioned load-balancing resource, depending on the Kubernetes environment and cloud provider.

# ExternalName

An **ExternalName** Service is different from the other Service types.

Instead of selecting Pods and forwarding traffic to them, an `ExternalName` Service acts as a **DNS alias** for an external DNS name.

It does not:

- Select Pods.    
- Create Pod endpoints.
- Load-balance traffic.
- Proxy requests to Pods.

Instead, Kubernetes DNS resolves the Service name to the specified external DNS name.

## Example

Imagine a web application running in Kubernetes that needs to communicate with an external OAuth2 identity provider.

You can create an `ExternalName` Service:

```yaml
apiVersion: v1
kind: Service

metadata:
  name: oauth-identity-provider

spec:
  type: ExternalName

  # External DNS name
  externalName: oauth2.provider.com
```

Applications inside the Kubernetes cluster can use the Kubernetes Service name:

```text
oauth-identity-provider
```

Kubernetes DNS resolves this name to:

```text
oauth2.provider.com
```

The flow can be represented as:

```text
Application Pod
       │
       ▼
oauth-identity-provider
       │
       ▼
Kubernetes DNS
       │
       ▼
oauth2.provider.com
```

This is useful when applications need to connect to external resources without embedding external hostnames throughout application configuration.

Possible use cases include:

- External APIs    
- OAuth or identity providers
- External databases
- Third-party services

# Service Type Comparison

| Service Type   | Primary Use Case                      | Accessible From                                   | Load Balancing                 |
| -------------- | ------------------------------------- | ------------------------------------------------- | ------------------------------ |
| `ClusterIP`    | Internal application communication    | Inside the cluster                                | Yes, across selected endpoints |
| `NodePort`     | External access through a node port   | Outside the cluster via node IP                   | Routes traffic to backend Pods |
| `LoadBalancer` | Public or external application access | Outside the cluster via an external load balancer | Yes                            |
| `ExternalName` | DNS alias for an external service     | Inside the cluster through DNS                    | No Pod-level load balancing    |


# Key Takeaways

- Pods are ephemeral, and their IP addresses can change.    
- A **Service** provides a stable network endpoint for accessing a dynamic group of Pods.
- Services use **label selectors** to identify the Pods they should target.
- Applications inside a cluster can usually communicate using **Service DNS names** instead of Pod IP addresses.
- `port` is the port exposed by the Service.
- `targetPort` is the port on which the application inside the target Pod listens.
- `ClusterIP` is used for internal cluster communication.
- `NodePort` exposes a Service through a port on Kubernetes nodes.
- `LoadBalancer` integrates with external load-balancing infrastructure to expose applications externally.
- `ExternalName` provides a DNS alias for an external service and does not route traffic to Pods.

## Conclusion

Kubernetes Services are essential for networking and communication within a cluster. They provide an abstraction layer between clients and dynamically changing Pods.

The main Service types serve different purposes:

- **ClusterIP** provides internal communication between applications and Services.
- **NodePort** provides external access through a port on Kubernetes nodes.
- **LoadBalancer** is commonly used to expose applications externally through load-balancing infrastructure.
- **ExternalName** provides a DNS-based way to reference external services.

By using Services, applications can communicate reliably without depending on individual Pod IP addresses, even when Pods are frequently created, removed, or replaced.
