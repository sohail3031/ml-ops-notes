In this topic, we will explore the components that make up a Kubernetes cluster and how they work together. You will learn about their individual functions and how each component communicates with the rest of the cluster.

Understanding the components of a Kubernetes cluster and how they interact is essential for deploying and managing applications in a containerized environment.

## Control Plane Components

The first set of components in a Kubernetes cluster is the **control plane**.

> [!NOTE]  
> The control plane manages the overall state of the cluster and makes global decisions, such as scheduling workloads and responding to cluster events.

Control plane components manage the cluster's state and determine how resources should be allocated. They ensure that the cluster maintains its desired state and coordinate communication between different components.

### `kube-apiserver`

The `kube-apiserver` processes requests from Kubernetes clients.

Kubernetes uses a **hub-and-spoke API pattern**, where the API server acts as the central control and coordination point for communication within the cluster. It is the primary interface for interacting with Kubernetes.

The API server receives requests to:

- Create resources.
- Retrieve resources.
- Update resources.
- Delete resources.

It also coordinates communication between Kubernetes components. For example, components such as the `kubelet` communicate with the API server to report their status and receive instructions.

> [!IMPORTANT]  
> The Kubernetes API server is the central communication hub of the cluster.

### `etcd`

Cluster state and configuration data are stored in the `etcd` data store.

`etcd` is a distributed key-value store that holds the data required for the cluster to function correctly, including:

- Cluster configuration.
- Pod configuration.
- Network configuration.
- Network policies.
- Resource state and metadata.

`etcd` serves as the **single source of truth** for the Kubernetes cluster.

> [!WARNING]  
> Because `etcd` stores the cluster's critical state, protecting and backing up its data is essential.

### `kube-controller-manager`

The `kube-controller-manager` ensures that the cluster continuously maintains its desired state.

It does this by running multiple controllers, including controllers responsible for:

- Replication.
- Endpoints.
- Namespaces.
- Jobs.
- Other Kubernetes resources.

For example, when you create a `Job`, which represents a one-time task, the Job controller creates the required Pods and ensures that the task runs to completion.

The general responsibility of a controller is to compare the **desired state** with the **current state** and take corrective action when necessary.

### `cloud-controller-manager`

The `cloud-controller-manager` connects a Kubernetes cluster to a cloud provider's APIs.

It runs cloud-specific controllers. For example, a `Service` controller can create, update, and delete cloud load balancers.

For workloads that run entirely in a local or on-premises environment, this component may not be required.

### `kube-scheduler`

The `kube-scheduler` assigns Pods to nodes in the cluster.

When scheduling a Pod, it considers several factors, including:

- Resource requirements.
- Available node resources.
- Hardware constraints.
- Software constraints.
- Policy constraints.
- Affinity and anti-affinity rules.
- Data locality.
- Inter-workload interference.

The scheduling process generally involves two main stages:

1. **Filtering** — The scheduler identifies nodes that are capable of running the Pod.
2. **Scoring** — The scheduler evaluates the feasible nodes and assigns them scores.

The scheduler then selects the highest-scoring node and schedules the Pod onto it. Finally, it records this scheduling decision through the API server.

## Node Components

Node components include:

- `kubelet`
- `kube-proxy`
- A container runtime

These components run on every node and manage the Pods and application containers running on that node.

A node can be a physical or virtual worker machine. It provides resources such as:

- CPU.
- Memory.
- Storage.

### `kubelet`

The `kubelet` is an agent that runs on every node in the Kubernetes cluster.

It manages the Pods running on the node and helps ensure that the containers and Pods are running as intended.

The `kubelet` receives Pod specifications (`PodSpecs`) and ensures that the containers described in those specifications are running.

Its responsibilities include:

- Ensuring that containers are running.
- Monitoring container and Pod health.
- Working with health checks, such as liveness and readiness probes.
- Restarting or recreating containers when necessary.
- Reporting node and Pod status.
- Handling node registration with the cluster.

> [!NOTE]  
> The `kubelet` is responsible for ensuring that the actual state of Pods running on a node matches their desired state.

### `kube-proxy`

The `kube-proxy` runs on each node in the cluster and manages network connectivity between Pods and Services.

It manages network rules and connections on the node's network stack to route traffic to the appropriate destination.

Its functionality can also be replaced by certain network plugins that provide equivalent service-routing capabilities.

### Container Runtime

The **container runtime** manages the lifecycle of containers on a node.

Its responsibilities include:

- Pulling container images.
- Creating containers.
- Starting containers.
- Stopping containers.
- Restarting containers.
- Deleting containers.

Kubernetes supports container runtimes that implement the **Container Runtime Interface (CRI)**, including:

- `containerd`
- `CRI-O`

The container runtime communicates with the `kubelet`, receiving instructions about which containers to start, stop, restart, or delete. It also reports container status information back to the `kubelet`.

## Add-on Components

Beyond the core Kubernetes components, **add-ons** extend Kubernetes by providing additional functionality.

Add-ons can provide features such as:

- Networking.
- DNS and service discovery.
- Monitoring.
- Metrics.
- Certificate management.
- User interfaces.
- Virtual machine support.

For example, instead of relying on `kube-proxy` for networking functionality, a networking solution such as **Cilium** can provide additional networking and security capabilities.

### Cluster DNS

One of the most important add-on components is **cluster DNS**, which is required for service discovery.

Cluster DNS provides DNS records that allow Pods and Services to discover and communicate with each other.

**CoreDNS** is commonly used as the in-cluster DNS server.

### Other Add-ons

#### Networking Add-ons

Networking add-ons provide cluster networking capabilities and allow Kubernetes to work with different networking topologies and technologies.

#### Kubernetes Dashboard and Headlamp

A graphical user interface can be used to interact with a Kubernetes cluster.

The Kubernetes Dashboard project has been retired, but alternatives such as **Headlamp** can provide a web-based user interface for managing and observing Kubernetes clusters.

#### `kube-state-metrics`

The `kube-state-metrics` agent connects to the Kubernetes API server and exposes metrics about the state of Kubernetes objects.

#### KubeVirt

**KubeVirt** is an add-on that allows you to run and manage virtual machines on Kubernetes.

#### `cert-manager`

`cert-manager` provides certificate management capabilities for Kubernetes clusters.

You can also develop your own add-ons to meet specific requirements.

## `kubectl`

Although `kubectl` is not a core or add-on component of a Kubernetes cluster, it is the primary command-line interface for communicating with the Kubernetes API.

It allows you to:

- Deploy resources.
- Inspect resources.
- Update resources.
- Delete resources.
- Manage the Kubernetes cluster.

## Installing `kubectl` on Windows

For Windows, you can download your preferred version of `kubectl` or use `curl`.

```shell
curl.exe -LO "https://dl.k8s.io/release/v1.35.0/bin/windows/amd64/kubectl.exe"
```

> [!NOTE]  
> Replace `v1.35.0` with the version of Kubernetes you want to install.

After downloading `kubectl.exe`, add the folder containing the executable to your `PATH` environment variable.

Verify the installation with:

```shell
kubectl version --client -o yaml
```

## Installing `kubectl` on Linux

For Linux, download the latest stable version using:

```shell
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
```

Install `kubectl` using:

```shell
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
```

Verify the installation with:

```shell
kubectl version --client -o yaml
```

## Common `kubectl` Commands

`kubectl` provides a high-level interface for managing a Kubernetes cluster.

### List Cluster Nodes

```shell
kubectl get nodes
```

Lists all nodes in the cluster.

### Create or Update a Resource

```shell
kubectl apply -f service.yaml
```

Creates or updates a Kubernetes resource defined in `service.yaml`.

### Get Information About a Pod

```shell
kubectl get pod my_pod
```

Retrieves information about the specified Pod.

### View Cluster Information

```shell
kubectl cluster-info
```

Displays information about the control plane and core services, such as the cluster DNS service.

> [!TIP]  
> You can use `kubectl` for most common Kubernetes management tasks without interacting with the Kubernetes API directly.

## Interacting Directly with the Kubernetes API

In some situations, you may want to interact with the Kubernetes API directly.

You can do this using:

- `curl`
- Client SDKs
- Custom applications

Kubernetes provides client libraries for languages such as:

- Python
- Go

Direct API access provides greater flexibility and control when interacting with the cluster. However, it also requires a deeper understanding of the Kubernetes API, its resources, authentication, and request structure.

## Summary

A Kubernetes cluster consists of several components that work together to deploy and manage containerized applications.

The main categories of components are:

- **Control plane components** — Manage the overall state of the cluster and make global decisions.
- **Node components** — Run on worker nodes and manage Pods and containers.
- **Add-on components** — Extend Kubernetes with additional functionality such as networking, DNS, metrics, and certificate management.

The `kubectl` command-line tool is the primary interface used to communicate with and manage a Kubernetes cluster.

> [!SUMMARY]  
> Understanding Kubernetes components and how they communicate is essential for effectively deploying, managing, troubleshooting, and maintaining Kubernetes clusters.
